# AI 应用开发岗位 - 项目经历整理

## 一、推荐定位

### 项目名称

**RAG 增强的 AI 全栈应用生成平台**

不建议继续使用“零代码网络生成平台”。“网络生成”表意不准确，“零代码”也会弱化项目中的 AI 工程、后端架构和可靠性建设。

### 项目身份

**个人项目 / 核心开发，2026.08 - 至今**

独立设计并实现 RAG、生成任务可靠性、代码流、自动修复、版本系统和托管数据运行时等核心模块。

### 技术栈

**Java 21、Spring Boot 3、LangChain4j、Reactor/SSE、MySQL、MyBatis-Flex、Redis、Flyway、Vue 3、TypeScript、Monaco Editor、RAG、Tool Calling**

按版面空间可删去 Flyway、MyBatis-Flex 和 Monaco Editor，但建议保留 Reactor/SSE、RAG、Tool Calling，这三项与 AI 应用开发岗位匹配度更高。

## 二、可直接放入两页简历的版本

### 项目介绍

面向非技术用户的 AI 全栈应用生成平台。用户输入自然语言需求后，系统自动完成需求规划、代码生成、实时预览、构建修复和版本管理；可按应用开启 RAG，检索历史需求与项目代码辅助增量修改，并通过托管数据模型、通用 CRUD API 和运行时 SDK，使生成结果从静态页面扩展为具备数据持久化、用户登录和权限控制的应用。

### 主要工作

- **设计并实现 AI 代码生成链路：** 基于 LangChain4j Tool Calling 拆分“创建”与“修改”两类提示词、AI Service 与最小工具集，创建阶段仅开放写入和结束工具，修改阶段再开放目录读取、文件读写、修改和删除工具，降低无效调用、工具幻觉及覆盖既有代码的风险。
- **设计并实现应用级 RAG：** 对源码与历史对话执行 ETL、重叠切片和 SHA-256 去重，采用关键词召回与可选 Embedding 语义召回，并通过 RRF 融合排序选取 Top 6 片段注入生成上下文；按 `appId` 隔离知识库，Embedding 异常时自动降级为关键词检索，不阻断主生成链路。
- **实现可恢复的流式任务系统：** 将生成任务、步骤、文件、进度和错误状态持久化，后端主动订阅模型流并通过 SSE 向前端转发结构化文件增量事件；支持断线重连、刷新恢复、中止与继续，解决浏览器连接中断导致生成状态和结果丢失的问题。
- **实现“生成 - 验证 - 修复”闭环：** 对 Vue 项目执行依赖与构建检查，将构建日志反馈给 AI，最多进行 3 轮自动修改与复检；同时提供自动版本快照、任意版本 Diff、单文件恢复和整版本回滚，降低 AI 修改代码的不可控风险。
- **实现托管数据运行时：** 支持 AI 在后台规划数据模型，提供模型发布、通用 CRUD/分页查询、应用用户登录与 RBAC，并为生成项目注入前端运行时 SDK，使 AI 生成应用能够安全访问持久化数据，而非停留在纯前端 Mock 页面。
- **实现 AI 开发工作区与安全边界：** 使用 Monaco Editor、完整目录树和可拖动分栏展示实时生成代码，集成 Console/Network/Build 调试信息；统一校验文件相对路径、保护目录、大小和数量限制，并通过 iframe sandbox 隔离生成页面与主站运行环境。

## 三、版面紧张时的四条精简版

- 基于 LangChain4j Tool Calling 设计并实现代码生成链路，拆分创建/修改提示词、AI Service 与最小工具集，并解析流式工具调用参数，将文件级增量事件通过 SSE 实时同步至前端目录和编辑器。

## 四、招聘平台项目详情版

该项目覆盖从自然语言需求到可部署应用交付的完整链路。系统按创建和修改场景拆分模型职责与工具权限，并将模型输出解析为文件级结构化事件；引入持久化任务模型，使模型调用与浏览器连接解耦，并提供断线恢复、中止/继续、构建检查和自动修复闭环。在上下文工程方面，实现应用级 RAG，将历史需求和已有代码按需召回，避免每轮请求都将完整项目塞入 Prompt。最后实现版本 Diff、Monaco 工作区、隔离预览以及托管数据运行时，成为可持续修改、可验证、可恢复的 AI 全栈应用 Builder。

## 五、面试时的核心讲法

### 1. 为什么要拆分创建和修改模式？

创建项目需要从零输出完整文件，修改项目则需要先理解已有目录并尽量局部变更。两者共用工具会增加上下文噪声和误调用概率。因此我让创建模式只拿到 `writeFile`、`exit`，修改模式才获得读取、修改、删除等 6 类工具，并分别维护系统提示词和 Service 缓存键。

### 2. 为什么 RAG 不直接把全部代码塞入 Prompt？

完整代码会快速占满上下文，也会让不相关文件干扰模型判断。当前方案将代码与对话分来源持久化，源码按约 1800 字符切片并保留 180 字符重叠；查询侧对英文词和中文 2～4 gram 分词，再结合可选语义向量召回，用 RRF 融合排名，最终只注入 Top 6 片段。

### 3. RAG 的可用性怎么保证？

RAG 是增强链路，不能成为代码生成的单点故障。系统默认可只使用本地关键词召回；启用 Embedding 后才增加语义召回，外部 Embedding 调用失败会自动降级。知识库按 `appId` 隔离，开启时自动补建旧项目代码索引，生成成功后重建代码索引，删除应用时同步物理清理 RAG 数据。

### 4. SSE 断开后为什么任务还能继续？

浏览器不再直接拥有模型流的生命周期。后端主动订阅生成流，把事件写入 `Sinks.Many` 并同步更新 `generation_task`；浏览器只是观察者。页面重开后先查询最新任务，再重新订阅任务事件并同步文件，因此网络断开不等于取消生成。

### 5. 自动修复为什么限制为 3 轮？

每轮会将真实构建日志反馈给修改模式 AI，修改后重新执行构建。无限循环会造成不可控的 Token 和时间消耗，所以设置最大轮数，并持久化当前轮次、构建状态和日志；达到上限后停止并保留诊断信息给用户处理。

### 6. 如何控制 AI 文件工具的风险？

所有路径先转为项目根目录下的规范化相对路径，并校验最终路径不能逃逸根目录；同时保护依赖、构建产物和关键配置目录，限制单文件大小、项目文件数量及可操作扩展名。预览使用独立 URL 和 iframe sandbox，避免生成脚本直接影响主应用。

### 7. 托管数据运行时解决了什么问题？

纯前端生成器只能展示 Mock 数据。当前平台把数据模型作为独立元数据发布，再通过通用 CRUD API 操作记录；生成项目使用统一 SDK 访问接口，平台负责应用级用户、会话和 RBAC。这样不需要每生成一个应用就重复生成并部署一套后端服务，也便于统一做鉴权和数据隔离。

## 六、当前简历中必须调整的内容

### 建议删除或改写

1. **删除“Qdrant 向量检索”**：当前代码没有接入 Qdrant，向量随 RAG 切片持久化在现有数据模型中。Qdrant 只是后续可替换的存储方案。
2. **删除“Hit@5 达 83%、部署成功率提升 18%”**：当前仓库没有对应评测集、基线、实验脚本和报告，面试时无法复现与解释。
3. **谨慎保留 ARMS、Prometheus、Grafana**：当前工作区没有对应依赖和配置。只有在你确实独立搭建、运行过并能展示监控指标时才保留。
4. **谨慎保留“输出护轨质量校验和自动重试”**：目前最明确的是输入 Prompt 安全护轨；构建失败自动修复属于另一条链路，不应混写成输出护轨。
### 推荐替换

- 将“基于 RAG 记忆增强的零代码网络生成平台”改为“RAG 增强的 AI 全栈应用生成平台”。
- 技术栈补充 `Reactor/SSE`、`Vue 3`、`TypeScript`、`Monaco Editor` 和 `Tool Calling`。
- 删除过长的通用项目介绍，把版面让给 AI 架构、RAG、可靠性和自动修复四类高含金量实现。
- 项目经历控制在 5～6 条，每条采用“解决什么问题 + 如何实现 + 得到什么工程结果”的结构。

## 七、后续补充量化数据的方法

当前可以使用“Top 6”“最多 3 轮”“创建 2 个工具/修改 6 个工具”“单文件 300 KB、单项目 300 文件”等可由代码直接验证的结构化数字，但不要将它们包装成业务提升率。

若希望后续补充效果指标，建议建立固定的 20～50 条生成与修改任务评测集，对比改造前后：

- 首轮构建通过率；
- 自动修复成功率和平均修复轮数；
- 无效/未知工具调用次数；
- 刷新或断线后的任务恢复成功率；
- RAG 检索 Recall@K / MRR，以及开启 RAG 前后的需求遵循率；
- 单次任务 Token 消耗与完成时延。

只有保留评测输入、基线版本、运行日志和统计脚本后，才建议把提升百分比写入简历。
